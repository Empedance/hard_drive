# Cloud Disk — Full-Stack Development Instructions

Act as a principal software architect and senior full-stack engineer. Build Cloud Disk, a secure, multi-tenant organizational cloud-storage SaaS platform inspired by Microsoft OneDrive and the Windows "This PC" interface.

## 1. Existing Project Context — Read First

I have already created the initial project directories:

- `CLAUDE.md`
- `one-drive-bakend/`
- `one-drive-frontend/`
- `one-drive-super-admin-frontend/`

The backend directory contains an existing project structure based on the architecture and conventions used in our institution. I have not implemented the frontend applications yet.

**These existing directories are intentional. Do not rename them, replace them, or impose a different repository structure.**

Before writing code:

1. Read `CLAUDE.md` completely.
2. Inspect the existing backend directory and its files.
3. Identify the backend's Java packages, naming conventions, layers, entities, DTOs, services, repositories, controllers, configurations, security patterns, exception handling, and database conventions.
4. Inspect existing dependencies, build configuration, database migrations, and application configuration.
5. Determine what is already implemented and what is missing.
6. Follow the established backend architecture consistently throughout Cloud Disk.
7. Preserve working code and existing conventions unless a change is necessary and justified.
8. Create the internal frontend structures yourself because both frontends are currently unimplemented.
9. Decide the remaining internal project organization based on the actual codebase and application requirements.

Do not assume the backend uses a particular package name, folder structure, authentication mechanism, or database schema before inspecting it.

Do not create a replacement backend architecture merely because you prefer another convention.

If the existing architecture conflicts with an essential security or functional requirement, explain the conflict and propose the smallest appropriate change before proceeding.

## 2. Technology Requirements

### Backend

Use the technologies already established by the existing backend project wherever possible.

The intended stack is:

- Java and Spring Boot.
- Maven, if consistent with the existing backend.
- Spring Web and REST APIs.
- Spring Data JPA and Hibernate.
- MySQL.
- Spring Security.
- DTO-based request and response models.
- Bean Validation.
- Database migrations, following the existing project conventions.
- OpenAPI/Swagger where appropriate.
- JUnit and Mockito for testing.

Do not introduce competing frameworks, duplicate existing modules, or unnecessarily upgrade working dependencies.

If the backend currently uses a different compatible technology or convention, inspect it and explain your recommendation before making major changes.

### User frontend

Create the application inside the existing `one-drive-frontend/` directory.

Use React, TypeScript, and Vite unless an existing project configuration dictates otherwise.

Build a complete user-facing cloud-storage application with a Windows-inspired file-management interface.

### Super Admin frontend

Create the application inside the existing `one-drive-super-admin-frontend/` directory.

Use React, TypeScript, and Vite unless there is a justified alternative.

Build a separate administrative application for platform operators.

Both frontends must use the same backend APIs and security model. Keep their interfaces and access permissions appropriately separated.

### Cloud storage

Use Backblaze B2 as the actual object-storage provider.

Inspect current provider documentation and supported APIs before implementing the integration. Keep storage-provider credentials on the backend.

## 3. Cloud Disk Product Requirements

Cloud Disk is an organizational cloud-storage service, not a general consumer file-sharing application.

### Organization onboarding

Implement an organization registration and activation workflow.

1. A prospective organization administrator registers.
2. They submit the organization details and administrator information.
3. Their email is verified.
4. The organization and owner account are created.
5. Storage provisioning is initiated and its status tracked.
6. The owner can sign in after the required activation steps succeed.
7. The owner is directed to the Cloud Disk user interface.

Provide appropriate handling for incomplete onboarding, provisioning failures, retries, and account activation.

Never store plaintext passwords or hardcode production credentials.

### User interface — Windows-inspired This PC

The main screen after login must resemble Windows File Explorer's "This PC" view.

Create:

- A top navigation bar with breadcrumbs, search, upload, notifications, and a profile menu.
- A collapsible left sidebar.
- Quick-access folders and favorites.
- Recents.
- Photos.
- Documents.
- Shared with Me.
- Shared by Me.
- Trash.
- A central This PC view displaying virtual drives.
- File and folder browsing with list and grid views where appropriate.
- Sorting, search, navigation, loading states, and error handling.

Drive cards should display the drive letter, drive name, allocated capacity, used capacity, available capacity, and a blue storage-usage progress bar.

All displayed storage values must come from actual backend data.

The interface should be polished, responsive, accessible, and visually faithful to Windows file-management patterns without copying Microsoft branding.

### Virtual drives

Users should be able to create logical drives such as C:, D:, E:, and additional permitted drive letters.

These are virtual drives in Cloud Disk, not actual operating-system partitions.

The organization purchases a storage allocation. Its administrators divide that allocation among virtual drives.

Implement:

- Drive creation and naming.
- Drive-letter uniqueness within an organization.
- Storage allocation and reallocation.
- Capacity and usage reporting.
- Drive membership.
- Per-drive permissions.
- Safe drive deletion or archival.
- Prevention of capacity oversubscription.

Drive allocations must never exceed the organization's purchased capacity.

Capacity changes must not silently delete data or violate existing storage usage constraints.

### File and folder operations

Implement functional, backend-connected workflows for:

- Uploading files.
- Downloading files.
- Creating folders.
- Renaming and moving files and folders.
- Deleting files and folders.
- Trash and restoration where appropriate.
- Sharing files and folders.
- Viewing file metadata.
- Favorites and Recents.
- Photos and Documents views.

Use Backblaze B2 for actual file contents and the existing backend's database conventions for metadata.

Do not store file contents directly in MySQL.

Support large uploads where appropriate, with progress indicators, validation, retry handling, and reliable storage accounting.

Use private object storage and authorized, short-lived upload/download access.

### Organization members

Organization owners and authorized administrators must be able to invite and manage members.

Implement:

- Invitations.
- Member activation and deactivation.
- Role assignment.
- Drive assignment.
- Drive-level permissions.
- Access revocation.
- Relevant activity history.

A user may have access to selected drives without access to every drive in the organization.

Enforce all authorization on the backend. Frontend hiding of buttons is not a security mechanism.

### File sharing

Allow authorized users to generate file or folder share links.

Provide configurable expiration options, such as one hour, one day, seven days, and thirty days, plus custom expiration where permitted.

Support revocation, optional passwords, recipient restrictions, and appropriate access permissions.

Enforce expiration and revocation server-side. Use cryptographically secure tokens and avoid storing raw tokens in logs.

### Storage subscription and billing

The organization must be able to select storage capacity from a minimum of 1 TB to a maximum of 250 TB.

Create a draggable capacity selector with a numeric input alternative.

Display the selected capacity, price per TB, billing interval, estimated amount, applicable taxes, and confirmation action.

Store global pricing configuration in the database. Allow authorized Super Admin users to configure default pricing and organization-specific pricing overrides.

The effective price must use the applicable organization-specific override when valid and otherwise fall back to the global configuration.

Store historical pricing snapshots for subscriptions and invoices.

Calculate prices on the backend. Never trust a price submitted by the frontend.

Do not create a real payment integration until the payment provider and required credentials have been agreed upon. Use a clearly identified development adapter for local testing if necessary.

Purchased storage, drive allocations, and actual storage consumption must be modeled separately.

### User profile

Provide profile settings, organization settings, team management, subscription details, billing history, security settings, active sessions, and logout.

Only authorized organization roles may access sensitive organization or billing settings.

## 4. Backblaze B2 Integration

Implement a secure, testable object-storage integration.

Evaluate the bucket strategy before implementing it. The default recommendation is a dedicated private bucket per organization, with individual virtual drives represented through database metadata and isolated object-key namespaces.

Do not create a new bucket for every virtual drive.

Do not create a separate bucket for every member unless the requirements justify that complexity.

Implement reliable organization provisioning, upload, download, deletion, error recovery, retries, and storage reconciliation.

Keep the object-storage implementation separate from business logic so it can be tested with a mock or test storage adapter.

Account for partial failures between MySQL and Backblaze B2. Do not assume a database transaction can roll back an object-storage operation.

Never expose Backblaze credentials or permanent public object URLs to the browser.

## 5. Super Admin application

The Super Admin frontend must be a separate application inside `one-drive-super-admin-frontend/`.

It should provide:

- Platform dashboard.
- Organization onboarding and management.
- Organization and member details.
- Storage usage and provisioning status.
- Subscription and payment information.
- Global pricing configuration.
- Organization-specific pricing overrides.
- User and account management.
- Audit logs.
- Login and security-event monitoring.
- Search, filtering, and pagination.
- Authorized suspension and reactivation workflows.

Display real backend data rather than fabricated dashboard statistics.

Record relevant events such as authentication attempts, organization creation, drive changes, uploads, downloads, deletions, sharing, billing changes, and administrative actions.

Audit logs must not expose passwords, secrets, raw session identifiers, or signed URLs.

Super Admin access to customer file contents must not be automatic. Exceptional access must be explicitly authorized, limited, justified, and audited.

Use dedicated administrative authorization rules on the backend.

## 6. Architecture and Implementation Rules

Follow the existing backend's architecture and conventions.

For the frontends, create a clean internal structure suitable for the application's complexity. Use reusable components, typed API contracts, consistent validation, centralized error handling, and appropriate server-state management.

Before introducing a new library or architectural abstraction, inspect what already exists and explain why the addition is necessary.

Do not duplicate existing utilities, security mechanisms, entities, or configuration.

Use database migrations consistently with the existing backend.

Every tenant-owned resource must have a defensible organization ownership path. Prevent cross-organization access even when a user manipulates IDs in API requests.

Implement proper validation, authorization, concurrency protection, and idempotency for critical operations.

Do not introduce microservices without a concrete requirement.

## 7. Testing and Verification

Implement automated tests appropriate to the existing backend architecture and both frontends.

Verify:

- Authentication and authorization.
- Organization isolation.
- Organization onboarding.
- Drive allocation and capacity constraints.
- Upload and download.
- Storage usage calculations.
- Folder and file permissions.
- Sharing expiration and revocation.
- Pricing and billing calculations.
- Administrative access controls.
- Error handling and storage-provider failures.

Run the actual available backend and frontend tests, linting, type checks, and production builds.

Fix failures introduced by your changes.

Never claim a test passed unless it was executed successfully. Clearly identify anything that remains untested because of missing services or credentials.
